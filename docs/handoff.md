## 1. プロジェクト概要

### 1.1 プロジェクト名

**sphere is learning**

### 1.2 目的

C++とDirectXを用いて、ゲームシミュレーターおよびAI学習・評価フレームワークを開発する。

本プロジェクトでは、3D空間での見下ろし方障害物回避ゲームを題材として、以下の技術を実践的に習得・活用する。

- C++によるソフトウェア設計・実装
- Direct3D 11による3D描画
- ゲームシミュレーションの設計
- ゲームAI・機械学習アルゴリズムの実装
- 処理の高速化・並列化
- 実験環境の構築と性能評価

最終的には、ゲームプログラマ職への就職活動で提出できる技術作品を目指す。

### 1.3 制作の背景

これまでUnity/C#を用いた2DカードRPG『DRAW WORLD』の開発に携わり、ゲーム全体のプログラミングを担当してきた。

一方、C++によるゲーム開発や3Dグラフィックス、ゲームAIの実装経験は比較的少ない。

そこで、既存の制作経験を補完する作品として、C++を用いたゲームシミュレーターとAI学習環境を新たに開発する。

また、大学2年時にはJavaを用い、Mario AI Competitionの環境で遺伝的アルゴリズムを実装した経験がある。

本プロジェクトでは、この経験を発展させ、ゲーム環境自体の開発からAIの学習・評価までを行う。

### 1.4 開発期限

**2026年11月16日：就職活動のES提出期限**

この時点で完全に開発が終了している必要はない。

ただし、動作するプロトタイプと、技術的に説明できる開発成果を用意することを目標とする。

期限内には、1ステージで遺伝的アルゴリズムによる学習を重ね、ゲームプレイが向上する様子をデモとして紹介できる状態を目指す。ステージクリアの達成は必須としない。学習結果の保存と、保存したAIを画面上で再実行する機能も必要とする。

開発時間は週15時間を目標とし、期限までは約4週間・約60時間を計画の目安とする。

## 2. ゲームの企画

### 2.1 基本コンセプト

*World's Hardest Game：*[https://www.coolmathgames.com/0-worlds-hardest-game](https://www.coolmathgames.com/0-worlds-hardest-game)　のような、障害物を回避しながらゴールを目指すゲームを制作する。

プレイヤーは球体で表現され、フィールドの下部からスタートして移動する障害物を避けながら上部のゴールへ向かう。

ゲームの複雑さを抑え、AIの学習や評価に適したシンプルなルールを採用する。

### 2.2 ゲーム画面

ゲームは3Dで描画する。

ただし、ゲーム内の移動は基本的に2次元平面上で行う。

カメラは斜め上からフィールドを見下ろす固定視点とする。

使用するオブジェクトは、基本的に球体と直方体に限定する。

| オブジェクト | 形状                              |
| ------ | ------------------------------- |
| プレイヤー  | 球体                              |
| 障害物    | 球体・直方体                          |
| 壁      | 直方体                             |
| 床      | 直方体                             |
| ゴール    | 色の異なる領域または立体（ゴールテープのようなものが作りたい） |

複雑な3Dモデル、テクスチャ、アニメーションは初期段階では実装しない。

### 2.3 ゲームルール

初期仕様は以下とする。

1. プレイヤーはフィールド下部のスタート地点から開始する。
2. WASDを基本操作とし、押している間は一定速度で移動し、離すと即座に停止する。上と右の同時入力なら右上へ移動するなど、斜め移動にも対応する。人間・AIともに8方向と停止の9行動にそろえる。斜め方向の速度の正規化と、相反するキーの同時入力の扱いは設計時に決定する。
3. フィールド内には移動する障害物が存在する。
4. 障害物に接触すると失敗となる。
5. ステージごとに時間制限を設け、これをオーバーした場合も失敗となる。
6. 壁を通り抜けることはできない。接触しても跳ね返らず、壁の先には進めない。
7. フィールド上部のゴールに到達すると成功となる。見た目はゴールを渡り切る表現を目指し、内部的には直方体のゴール判定領域への接触で判定する。判定領域の配置は見た目と整合させる。
8. 成功・失敗後は、人間のプレイ時も待ち時間や再開操作なしで自動的に再開する。
9. 同じシミュレーションステップで複数の終了条件が成立した場合は、成功、障害物との衝突、時間切れの順に優先する。

制限時間は初期仕様に含める。具体的な秒数と境界時刻の扱いは設計時に決定する。チェックポイントは将来の検討事項とする。再開時はプレイヤー、経過時間に加え、障害物の位置・移動方向・移動位相も初期状態へ戻す。

### 2.4 障害物

最初のステージでは、床面内の上下または左右に一定の経路を往復する障害物のみを採用する。

初期実装の対象：

- 左右を往復する立方体
- 上下を往復する直方体

将来の候補（初期実装には含めない）：

- 一定の円軌道を移動する球体
- マリオシリーズの「ファイバー」のように、回転する細長い直方体
- マリオシリーズの「ドッスン」のように、y軸方向に上下移動する直方体

上記の「y軸方向」は床面に垂直な高さ方向を意味する。床面内の上下移動とは区別する。

障害物の位置・速度・移動周期などは設定可能にする。

### 2.5 ステージ

初期段階では1つのステージを制作する。

その後、AIの汎化性能を評価できるよう、障害物の数・位置・速度などを変更した複数のステージに対応させる。

ステージ構成を変更しても、ゲームシミュレーター本体のコードを変更する必要がない設計を目指す。

描画なしのシミュレーションではCLIからステージを指定し、人間がゲームとして遊ぶ際はステージ選択画面を用意する。初期段階では選択対象が1ステージでもよい。ステージデータの形式は設計時に決定する。

## 3. システム設計方針

### 3.1 開発技術

| 項目          | 採用技術                                     |
| ----------- | ---------------------------------------- |
| プログラミング言語   | C++20                                    |
| ビルドシステム     | CMake                                    |
| 3D描画        | Direct3D 11                              |
| 描画補助ライブラリ   | DirectXTK                                |
| デバッグGUI     | Dear ImGui                               |
| バージョン管理     | Git / GitHub                             |
| 初期AIアルゴリズム  | 遺伝的アルゴリズム                                |
| 将来的な学習ライブラリ | Python / Gymnasium / Stable-Baselines3など |

技術選定は開発中に見直す可能性がある。

### 3.2 シミュレーションと描画の分離

本プロジェクトで特に重視する設計方針。

ゲーム内部のシミュレーション処理と、DirectXによる描画処理を独立させる。

シミュレーション処理には、以下を含む。

- プレイヤー・障害物の位置管理
- プレイヤーの移動
- 障害物の移動
- 衝突判定
- ゴール判定
- ゲーム状態の更新
- エピソードの終了判定

これらの処理は、DirectXを使用せずに実行できるようにする。

### 3.3 ヘッドレス実行

AIの学習時にはゲーム画面を描画せず、内部シミュレーションだけを高速に実行できるようにする。

画面描画のフレームレートに依存せず、可能な限り高速にゲームを進行させる。

また、将来的には複数のゲーム環境を同時に実行し、AIの学習・評価を並列化することも検討する。

### 3.4 シミュレーションの再現性

同じ初期状態・乱数シード・行動系列が与えられた場合、同じ結果を再現できる設計を目指す。

ゲーム状態の更新には固定タイムステップを使用する。

ただし、異なるCPUアーキテクチャやOS間での浮動小数点演算の完全一致は自動的には保証されないため、必要に応じて検証する。

### 3.5 AIとのインターフェース

AIがゲーム環境とやり取りするための共通インターフェースを実装する。

想定する操作は以下のとおり。

- `reset(seed)`：ゲームを初期化する
- `step(action)`：AIの行動を適用し、ゲームを1ステップ進める
- `getObservation()`：AIが観測できる状態を取得する

`step()`の結果には、報酬・成功判定・失敗判定などを含める方針とする。

自動再開によって、終了した試行の結果や最後の観測が失われないようにする。設計案としては、`step()`が終了結果を返し、呼び出し側が結果を記録してから待ち時間なしで`reset()`する構成を推奨する。内部で自動初期化するかどうかは、API設計時に確定する。

具体的なクラス構成やデータ型は、実装前の設計段階で決定する。

## 4. AI・機械学習

### 4.1 基本方針

ゲームシミュレーターをAIの学習・評価環境として利用できるようにする。

AIはゲームの状態を観測し、プレイヤーに対する操作を決定する。

初期段階ではC++で遺伝的アルゴリズムを実装する。

その後、必要に応じて別のアルゴリズムを追加する。

### 4.2 観測情報

AIはステージ全体の正確な状態ではなく、プレイヤー周辺の一定範囲を観測する。

周辺をマスに区切り、それぞれに何が存在するかを入力する方式とする。ユーザーが過去にMario AI Competitionの環境で実装した周辺マスの観測方式を参考とする。

観測範囲はプレイヤーの中心を含む3×3から開始する。当初は必要に応じて5×5へ変更できる方針だったが、行動表方式では5×5（自分を除く24マス）にすると4種類でも4²⁴通りになり表を作れないため、3×3で固定する。ゲーム内部の移動をマス単位にする要件ではなく、観測の表現として扱う。

当初は現在と時間的に少し前のマス情報をAIに与える案だった。2026年10月25日、ユーザーの方針により、観測は現在の時点だけとし、観測番号ごとに行動を定めた行動表を遺伝的アルゴリズムで最適化する方式へ変更した（4.5節）。行動表では、前回の8マスを加えると状況数が4¹⁶（約43億）通りになり扱えないためである。障害物の移動方向が必要になった場合は、マスの種類を「近づく障害物」「遠ざかる障害物」などに分けて表す方法を検討する。

現在だけの観測では、障害物が近づいているのか遠ざかっているのかを区別できない。この制約は、学習結果を説明するときに明記する。

ゴールは上方向で固定するため、ゴール方向を追加の入力として与えることは初期要件としない。上へ進むことを促す情報は報酬・適応度の設計で扱う。1マスの大きさ、占有判定方法、観測間隔の具体値は設計時に決定する。

### 4.3 行動

人間・AI共通で、以下の9種類の離散行動を用いる。

- 上
- 下
- 左
- 右
- 右上
- 右下
- 左上
- 左下
- 停止

斜め移動でも直進と同じ速さになるように移動ベクトルを正規化し、相反するキーは軸ごとに打ち消す案を推奨する。これは未確定の設計案とする。

### 4.4 報酬・評価

学習に用いる報酬の候補は以下のとおり。

- ゴール到達時の報酬
- ゴールへの接近に対する報酬
- 障害物に接触した場合のペナルティ
- 時間経過に対するペナルティ

報酬設計によって意図しない行動が学習される可能性があるため、実験に基づいて調整する。

また、AIの性能評価には以下を使用する。

- クリア率
- ゴール到達までのステップ数
- 累積報酬
- 未学習ステージに対する成功率
- 学習に要する時間
- シミュレーションの実行速度

期限内の中心的な評価は、同じ1ステージにおける学習前後・途中世代のゲームプレイの改善とし、ゴール方向への到達距離を主指標とする。未学習ステージでの評価は将来の拡張とする。

到達距離は改善を説明する主指標であり、報酬や遺伝的アルゴリズムの適応度を到達距離だけに限定する要件ではない。生存時間、左右の移動量なども報酬に含める可能性を残し、試行ごとの指標を分けて記録する。具体的な報酬項と重みは実験で調整する。

評価回数と乱数シードはCLIから指定可能にする。具体的なコマンド名、オプション、既定値は未定であり、CLIの定義時に日本語の仕様書と`--help`を整合させる。

### 4.5 遺伝的アルゴリズム

初期実装では、遺伝的アルゴリズムを使用してAIの行動方策を最適化する。

2026年10月25日、ユーザーの方針により、周辺観測の番号ごとに行動を定めた行動表を個体とする方式を採用した。ニューラルネットワークは使わない。表の1要素を見れば、その状況で選ぶ行動を説明できる。

#### 観測から行動まで

- プレイヤーを中心に周辺を3×3のマスに区切り、自分のマスを除く8マスを観測する。
- 各マスの内容を1バイトの種類で表し、8マスで合計8バイトとする。教材での種類は空き・壁・障害物・ゴールの4種類。重なった場合の優先順位（教材では障害物＞ゴール＞壁＞空き）を固定し、フィールド外は壁として扱う。プレイヤー自身は障害物として数えない。
- 8マスの並び順を固定する。教材では上の行の左→右、中央の行の左→右（自分のマスを除く）、下の行の左→右。
- 8マスの種類を種類数を基数とする8桁の数として番号へ変換する。4種類なら番号は0〜65535（4⁸通り）。8バイトをそのまま64ビット整数として使うと2⁶⁴通りとなり、表を作れない。
- 番号を添字、値を行動の番号（停止＋8方向の9行動、`Direc`の宣言順）とする配列を行動表とし、行動表1つを1個体とする。4種類なら1個体65,536バイト。初期個体は乱数シードを指定し、各要素を9行動から一様に選んで生成する。
- 種類を5つに増やすと表は5⁸＝390,625要素になる。観測方式の異なる保存済み個体を、そのまま別の方式で読み込まない。
- シミュレーションの更新間隔と、AIの行動決定間隔を明記する。決定した行動は次の行動決定まで維持し、描画速度で行動頻度を変えない。

1回の試行で訪れる観測は65,536通りのごく一部であり、訪れない要素の変化は成績に影響しない。訪れた状況の数を記録し、突然変異率の調整に使う。

#### 世代更新

以下の数値は動作確認のための開始候補であり、性能が検証された設定やCLIの既定値ではない。

| 項目 | 開始候補 | 意図 |
| --- | --- | --- |
| 個体数 | 64 | 小さな集団で学習と計測を開始する |
| エリート保存 | 上位4個体を変更せず次世代へ移す | 得られた方策を維持する |
| 親選択 | 3個体のトーナメント選択 | 適応度が負でも順位に基づいて選択する |
| 交叉 | 行動表の要素ごとの一様交叉 | 各要素を2親のいずれかから引き継ぐ |
| 突然変異 | 各要素を確率0.01で、9行動から一様に選んだ行動へ置き換える | 行動の番号には大小の意味がないため、値を加減せず置き換える |
| 終了条件 | 最大世代数または明示的な停止 | クリアできなくても学習を終了できるようにする |

初期集団を評価・保存した後、選択、交叉、突然変異、次世代の評価を繰り返す。個体の評価は、成功・衝突・時間切れまでの1試行で区切る。即時の自動再開は呼び出し側で行い、別試行の報酬を混ぜない。

すべての個体を同じステージ・初期状態・制限時間・評価条件で比較する。学習用乱数（初期個体、親選択、交叉、突然変異）と環境の乱数は分けて管理する。固定初期状態で方策も決定的なら同じ評価の繰り返しは同じ結果となり、評価回数だけ増やしても条件の多様性は増えない。必要なら学習用乱数シードを変えた独立した学習実験を行う。

#### 報酬・適応度・デモ用指標

各ステップの報酬、1試行から算出する適応度、デモで比較する到達距離を区別する。最初は累積報酬を適応度に用いる案とし、報酬計算は観測・行動・遺伝操作から独立させる。生存時間や左右の移動量などの項を変更しても、個体表現と世代更新の処理を変更しない構成とする。

到達距離の具体案は「試行中に到達した最も上の位置と開始位置の差」とし、最終位置とは区別する。前進への報酬は到達記録を更新した分に与えるところから始め、同じ場所の往復で何度も得点しないようにする。生存時間や左右の移動量を加点する際は、停止や左右の往復だけが有利にならないか、到達距離と合わせて確認する。

世代ごとの最良・平均適応度と到達距離、生存時間、左右の移動量、終了理由を記録する。左右の移動量は正味の変位か総移動距離かを明記する。適応度が最大の個体と到達距離が最大の個体が異なる場合は区別して保存する。報酬の重みを変えた実験間で、適応度の値だけを直接比較しない。

### 4.6 学習結果の保存・再実行

学習結果を保存し、読み込んだAIをDirect3D 11のゲーム画面上で再実行できるようにする。学習の進行による変化を比較できるよう、保存対象の世代や評価結果、ステージ・乱数シードなどの実行条件をどのように記録するか設計する。

設計案として、初期・途中・最終世代の代表個体を保存する。保存情報には行動表、観測のマス幅・マスの種類と優先順位・8マスの並び順・番号の変換方法、行動の対応順・決定間隔、ステージ設定、制限時間・固定時間刻み、乱数シード、報酬設定、世代番号、評価結果、形式のバージョンを含める。再実行時は保存条件を復元し、対応しない形式・構成はエラーにする。個体の保存だけでは学習の中断・再開に必要な集団全体や乱数生成器の状態は保存されない。

保存形式、学習の中断・再開、行動系列を記録した完全なリプレイは未確定とする。保存したAIを再実行する機能と、記録済みの行動系列を再生する機能は区別する。
